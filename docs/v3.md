# Template Engine V3 完整实施契约

适用接口：

```text
POST /v1/generate-next
POST /v1/update-next
```

适用源码：

```text
template-source/code/frontend/**
template-source/code/backend/**
```

本契约中的 **MUST / MUST NOT / SHOULD** 为实现约束，不是建议。

---

# 1. 总体边界

V3 与现有 V2 必须完全隔离。

迁移阶段：

```text
Legacy Template Source
        ↓
V2 Engine
        ↓
/v1/generate
/v1/update


template-source/code
        ↓
V3 Extension Engine
        ↓
/v1/generate-next
/v1/update-next
```

本阶段 MUST NOT 修改以下接口行为：

```text
POST /v1/generate
POST /v1/update
```

MUST NOT 修改以下 V2 核心类的语义：

```text
CapabilityV2Loader
V2ProjectGenerator
ReconcileDecisionEngine
TemplateStateV2
PackageBuilder
WireStrategyCompiler
```

---

# 2. 实施顺序：OpenAPI First

Codex 必须按以下顺序实施：

```text
Phase 0  冻结 V3 Wire Contract / OpenAPI
Phase 1  定义 V3 Core Model
Phase 2  CodeTemplateReleaseLoader
Phase 3  generate-next
Phase 4  Generate Parity Test
Phase 5  V3UpdatePlanner
Phase 6  update-next
Phase 7  Update Executor Contract Test
Phase 8  最终 Revision Gate 验收
Phase 9  全量 Legacy Regression
```

在 Phase 0 完成之前，MUST NOT 开始 Controller 和 Planner 实现。

Phase 0 必须先完成 OpenAPI、ZIP 内部 JSON Schema、`docs/REFACTOR.md`、本文件的冻结语义、双 Source `AGENTS.md`、README、Revision Gate 和 Contract Tests。Phase 8 再对两个 Revision Gate 做最终分支级验收。

# 3. OpenAPI：`generate-next`

接口：

```text
POST /v1/generate-next
Content-Type: application/json
Accept: application/zip
```

Request：

```json
{
  "requestedConfig": {
    "capabilities": {
      "authorization": {
        "enabled": true,
        "config": {}
      }
    }
  }
}
```

顶层只允许：

```text
requestedConfig
```

禁止额外字段。

## Capability Request

Schema：

```text
requestedConfig.capabilities
    map<string, CapabilityRequest>
```

CapabilityRequest：

```json
{
  "enabled": true,
  "config": {}
}
```

字段必须完整：

```text
enabled: boolean
config: object
```

规则：

```text
enabled = true
    → 加入 requested

enabled = false
    → 不加入 normalized requested
```

`config` 当前为 opaque JSON object：

* Engine MUST 保存；
* Engine MUST 参与 State equality；
* 当前 Login / Authorization 不消费 config；
* Engine MUST NOT 擅自解释 config。

Capability ID 为空字符串必须返回 `400 BAD_REQUEST`。

# 7. `effective`

`effective` 表示 dependency closure。

例如 requested：

```json
{
  "authorization": {
    "enabled": true,
    "config": {}
  }
}
```

如果：

```text

```

则 effective 必须为：

```json
{
  "login": {
    "enabled": true,
    "config": {}
  },
  "authorization": {
    "enabled": true,
    "config": {}
  }
}
```

隐式依赖 Capability：

```text

```

当前 Manifest 没有 `defaultConfig`，因此默认：

```json
{}
```

State 序列化时 Capability Key MUST 按字典序稳定输出。

# 10. installedRevision 语义

`installedRevision` 表示：

> 该 Artifact 实际复制进用户工程时所使用的模板版本。

Release Refresh 时，如果 Artifact 已存在于 State：

```text
MUST NOT 覆盖
MUST NOT 修改 installedRevision
```

例如：

```text
foo.ts
installedRevision = R1
```

R2 中 `foo.ts` 内容改变：

```text
State 仍保持 R1
用户工程 foo.ts 不动
```

这是明确设计，不是遗漏。

# 11. `managedContributions`

只记录：

> Manifest 投影到已有工程文件中的受管 Contribution。

V3 第一版只允许两种：

```text
JAVA_ANNOTATION
MAVEN_DEPENDENCY
```

Frontend generated registry 不进入此 State。

---

### Managed Contribution 按物理 Resource 聚合

同一物理 Contribution 可以被多个 Extension 声明，但最终工程中只维护一份。Managed Contribution 的身份由物理受管资源决定，不由声明它的 Capability 决定。

固定 Resource Key：

```text
annotation:<annotationClass>
maven:<groupId>:<artifactId>
```

State 使用非空、去重、按 Extension ID 字典序排列的 `owners: string[]`，不包含 `capabilityId`。每个 Owner 必须存在于 `effective`。

Loader/Resolver 得到 `effective` 后必须先构建唯一的：

```text
Map<ResourceKey, AggregatedManagedContribution>
```

同一 Resource 的 spec 相同则合并 Owner；spec 不同则 Release 加载失败。同一 Extension 重复声明同一个 Resource 返回 `TEMPLATE_SOURCE_INVALID`。Owner 与 Resource Key 均按字典序稳定排序。Generate、Update 和 State 必须消费同一份聚合模型。

同一 Maven coordinate 的 `version` 或 `scope` 不同，Release 加载失败并返回 `MAVEN_DEPENDENCY_CONFLICT`。

# 50. Contribution Diff

Planner 按 Resource Key 比较 `currentState.managedContributions` 与当前 Release 聚合结果，不按单个 Capability 分别比较。

旧 State 不存在、新聚合 State 存在：

```text
REMOVE_*
```

旧 State 存在、新聚合 State 不存在：

```text
ENSURE_*
```

旧、新 Resource 都存在且 spec 一致：

```text
无需 Operation
```

即使 owners 发生变化，也不得 REMOVE 或 ENSURE；只更新 next State 的 owners/appliedRevision。

旧、新 Resource 都存在但 spec 不一致：

```text
REMOVE old
ENSURE new
```

next State 保存新 spec。

仅当 owners 从非空集合变为 Resource 不存在时才允许 REMOVE。Generate 与 Update 中一个 Resource 只产生一份物理投影。

# 53. 合法 RECONCILE Operation

只允许：

```text

ENSURE_JAVA_ANNOTATION
ENSURE_MAVEN_DEPENDENCY
```

针对当前 State 中已经声明的 Managed Contribution。

不得输出：

```text

```


即使实际目标工程本来就是健康的。

# 55. Package Executor 原子性契约

调用方应用 V3 Update Package 时 MUST：

```text
1. 校验 currentStateDigest
2. 校验全部 payload size + sha256
3. 按 index 顺序执行 Operations
4. 任一 Operation 失败则整个 Package 失败
5. 所有 Operation 成功后才写 nextTemplateState
```

Package Apply 同时满足 Workspace Atomicity 与 Template State Atomicity。生产 Executor 必须采用事务式 Apply；可以通过：

```text
临时目录 / worktree / transaction workspace
```

实现 staging、提交和完整回滚。

调用方 Executor MUST 按以下顺序执行：

```text
preflight
→ staging / transaction
→ apply all operations
→ commit workspace
→ commit nextTemplateState
```

Preflight 必须在修改文件前验证 State Digest、Operation Schema、路径安全、payload 存在性与 size/SHA-256、index 连续性、operationId 唯一性和 Operation 支持性。Preflight 失败时不得修改任何文件或 State。

Apply 期间任何操作失败时，Workspace 必须恢复到 Apply 前的 byte-for-byte 状态，State 保持不变。仅保证 State 不推进但留下部分文件变更不符合 V3 契约。

MUST NOT：

```text
Operation 执行一半
却提前持久化 nextTemplateState
```

# 56. V3 HTTP Error Contract

使用现有 Error Envelope：

```json
{
  "code": "...",
  "message": "...",
  "details": {},
  "traceId": "..."
}
```

错误码按场景唯一映射，不允许由实现者在多个码之间选择：

| 场景 | HTTP | code |
| --- | ---: | --- |
| 非 JSON Object、字段缺失/多余、请求结构错误、非法 Capability ID、非法 mode | 400 | `BAD_REQUEST` |
| `protocolVersion` 是 String 但不等于 `3` | 400 | `PROTOCOL_VERSION_UNSUPPORTED` |
| `schemaVersion` 是 Integer 但不等于 `3` | 400 | `TEMPLATE_STATE_SCHEMA_UNSUPPORTED` |
| State 固定字段、内部结构、Resource Key 或自身一致性非法 | 400 | `TEMPLATE_STATE_INVALID` |
| Capability 不存在于当前 Release | 400 | `CAPABILITY_UNKNOWN` |
| Capability 移除 | 409 | `CAPABILITY_REMOVAL_UNSUPPORTED` |
| RECONCILE 需要 State Change | 409 | `RECONCILE_STATE_CHANGE_REQUIRED` |
| 当前 State Revision 高于服务端 Release | 409 | `TEMPLATE_RELEASE_DOWNGRADE_UNSUPPORTED` |
| Server V3 Template Source 非法 | 500 | `TEMPLATE_SOURCE_INVALID` |
| 前后端相同 ID Extension Contract 不一致 | 500 | `EXTENSION_CONTRACT_MISMATCH` |
| Maven Coordinate spec 冲突 | 500 | `MAVEN_DEPENDENCY_CONFLICT` |
| ZIP、序列化或 Package 构造失败 | 500 | `PACKAGE_BUILD_FAILED` |

不要新增多个同义 Error Code。
